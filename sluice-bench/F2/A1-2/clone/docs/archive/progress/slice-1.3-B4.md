# Slice 1.3-B4: board columns from ADO

**Status:** built 2026-10-27; waiting on HG-B (this item's part: `review/v1.3/B/B4-board.png`). Plan: [23-v1.3.md](../23-v1.3.md) Block B. Fixture data only (INV-18).

## 1. What was built
- **Parsing.** `RevisionFact` gains `boardColumn` (`System.BoardColumn`) and `boardColumnDone` (`System.BoardColumnDone`, kept only when true and a column exists). `parseBoards` / `parseBoardColumns` read the endpoints below (`src/shared/ingest/parse.ts`).
- **Endpoints (04 §3).** Per team: `GET {project}/{team}/_apis/work/backlogs`; the level with id `Microsoft.RequirementCategory` (else `type: requirement`) names the Stories board, whatever the process calls it (Basic's Issues, a renamed level); then `GET …/boards/{level name}/columns` (ADO accepts a level's name for `{board}`, which I could not check against a real ADO; two calls per team, not three). Read with the teams in `src/main/sync/boards.ts` (`readTeams`), stored as `TeamFacts.columns` in the `teams:` setting. Family `teams`: a 401 is a missing scope, quiet like the team's settings read (Work items read), not B2's builds; 403/404 mean none; a blip keeps the columns read before; nothing here fails a sync. The teams read runs beside a sync and **never before it**: the first look does not wait.
- **One team's board (review fix).** In a sprint whose pods belong to different teams, an item's placement counts only while its area belongs to the chosen team (`boardTeamOf(...).owns`, applied in `derive` and mirrored in the DSL); others use the ladder.
- **The bundle.** `ScopeHistory.board?: { columns, placements }` (03 §4). The scope's board is its team's: an area's path, or a sprint's first pod with a clear team that has a board (`boardColumnsOf`); an Epic has none. `placementsOf` / `boardOf` (`src/shared/ingest/board.ts`) are shared by `derive` and the fixture DSL (AC-27). **No event carries a column**, so Solar's inputs are untouched.
- **The v0 board (06 §3, 08 §6).** `board.ts` works in slots: the four ladder columns, or the team board's columns in order. **Split columns are honoured as two slots, `Name: Doing` and `Name: Done`** (chosen over one column with a mark). Each column's name is a faint heading over the first lane (`BoardSpec.columns`, DOM `.column-head`, neighbours alternating a line apart); the map key names them. Done compresses in an outgoing column. Min column share is `min(0.14, 0.9 / slots)`, so four columns are unchanged. A split column is **one heading with `Doing / Done` beneath** (review fix), over the first lane only: not repeated per lane and not part of label avoidance, so a ship or body can pass over it (in the still, a ship covers part of "Resolved").
- **Fallback.** Work with no column (no board, a refused call, never on a board, a column the board no longer has) keeps its ladder column, mapped onto the slots, monotonically (review fix): Ready to the first, Underway to the first In Progress, Nearing to the last In Progress but never left of Underway, Accomplished to the last (a two-slot board gives 0,1,1,1). With no board at all everything is exactly as before (4 slots, no headings).
- **Cache and first launch (review fix).** Migration `007_board_columns.sql` is `DELETE FROM item_checkpoints` only. An item with no checkpoint reads as having no history cached, and `putHistory` upserts, so each item's whole history is read again, lazily, the next time any path touches it, replacing the old facts. Scopes keep `lastSuccessAt`, members, current state, `levels:*`, derived tables and `teams:*`, so nothing blocks and the chart draws as before (work placed by state) until items are re-read. **`DERIVATION_VERSION` is not bumped (stays 1):** `derive`'s events, links and observations are identical; only the bundle gains `board`. **A user's first launch after B4:** the first sync, stream or refresh of each scope re-reads every item's history in full (one revisions and one updates call per item), as after 003 but without ever showing an empty or unsynced scope. The first look is unchanged. The cached team lists lack columns, so the first load refreshes them in the background and the headings appear on the load after that (an open scope may need a reload).
- **Fixtures.** The DSL gained `.board({ columns, byState })` (a state maps to a column, and to a Done half with `{ column, done: true }`), `.column(id, name, done)` (a column inside the state, **riding on the item's next revision** so no revision number or event key moves; the DSL throws if no revision of that item ever carries it), `BoardDef.level` (the fake's requirement level name), `teamsOfProject`, and `boardColumnFacts`. The fake ADO serves boards and columns (none for a scenario without a board) and `System.BoardColumn` / `BoardColumnDone` on revisions. Halcyon (`sprint-pods`): New, Ready, Active, Code Review (an item enters it when its PR opens while Active), Resolved (split; Ready to Accept is its Done half), Closed. `pod-sprint`: New, Ready, Active (split), Code Review, Resolved, Ready to Accept, Closed. `npm run fixtures` re-run; AC-27 holds.
- **Drive:** `tests/drive/steps/board-columns.ts` (`POD="Nova Pod" npm run drive -- tests/drive/steps/board-columns.ts --paradigm sprints`). Still: `review/v1.3/B/B4-board.png` (Nova Pod, end of sprint, first lanes; the full Quasar board is too wide to read headings at fit).

## 5. Known limitations and open questions
- The first look is never held for the team or board read, so a project's first sync may build its first bundle before the columns exist (ladder); the next load has them.
- Level-loaded items with no history yet (current state only) have no column: they use the ladder until history is read.
- A team whose Bugs show on the Tasks board has Bugs with no `BoardColumn`: they use the ladder slots among the board's columns.
- Headings use the first lane, so on a very wide board (Quasar, Pulsar) they are tiny at fit and read when zoomed in, like the rest of that board (08 §6 open row).
- Two teams owning one pod tie: no board (ladder).
