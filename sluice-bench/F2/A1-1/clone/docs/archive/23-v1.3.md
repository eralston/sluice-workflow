## How this doc works

One loop per block of feedback:
1. **Intake.** The user's notes go into §3 as a new block, nearly verbatim.
2. **Contextualize.** Before anything is built: drive the app (`npm run drive`), take stills of each
   surface the notes name, read the code, and fill each item's *Today* line. Check each note
   against the standing rules (§1).
3. **Ask.** Open questions go into §4, each with a recommendation. The user answers them (inline here,
   or in multiple-choice prompts), and the answers go into §5.
4. **Choose a build mode, per block** (decided 2026-10-14). The main session proposes one of these,
   with a rough time and cost, and the user picks:
   - **inline:** built in the conversation, with one fresh-context reviewer at the end;
   - **a workflow:** the v1.1 pipeline of implement → adversarial review → fix per item, then the full
     suite, an audit and a review set. It runs only if the user asks for it ("use a workflow" or
     "ultracode"). See [20](../20-agent-workflows.md) and [21](../21-ultracode-run.md).
5. **Build** one item (or a few sharing files) at a time. Each ends like any slice: checks passing, a
   note in `docs/progress/` (format: [progress/README.md](../progress/README.md)), and the item's State
   line here. Values go to [15](../15-reference.md) in the same change, and any departure from 02, 03 or
   13 is amended there and called out.
6. **Review.** End the block with stills of exactly what changed. Leave a human gate in §6 where the
   user's eye decides.

**Item ids:** a block's letter and a number (A1, B1, …). Fixture data only (INV-18).

## 1. Standing rules

The v1.1 rules stand: [13 §1, *v1.1 rules*](../13-game-design.md#design-pillars). In short:
- **R1.** Holo labels are the one visual language, in four tiers (15 §6; T4 Sky since 22 A5).
- **R2.** Visibility is separate from navigation.
- **R3.** The outside matches the inside.
- **R4.** Counts first, detail when it's known, with no reflow.
- **R5.** Progressive disclosure, in place.
- **R6.** One geometric vocabulary.
- **R7.** On screen means active.

Added by Block A (2026-10-14), from the live review's themes:
- **R8.** Every motion means something: a ship travels to a target, interacts, finishes, then moves on.
- **R9.** The drawn count is the true count: what a view draws matches what it counts, and nothing
  exists on the chart without a reason it can state.
- **R10.** Identity by more than one cue: colour, silhouette and place each say what a thing is, so
  it still reads when one cue is lost.
- **R11.** An object arrives before its label.

Added by Block B (2026-10-15):
- **R12.** One vocabulary, two layers: the ADO identity first, the metaphor beside it in lower
  contrast, the same on every surface. No switch between them.
- **R13.** Playback explains itself: every emphasized interaction names its ADO cause, in the same
  words as History.
- **R14.** Attention is budgeted: about two emphasized objects at a time, each held long enough to
  read.

A v1.3 block may add rules: they go here and into 13 §1 together.

## 6. Order and gates

**Order:** F (hygiene and tests, so every later block runs on a cleaner, greener suite; F1 is in place
before B4 needs it) → B → C → D → E → the close.

**Build mode: a workflow** (the user's choice, 2026-10-27; [20](../20-agent-workflows.md)). Per block, items
run **serially**, because e2e runs, keystone runs and drives all rebuild `out/`. Each item is
implement → a fresh adversarial reviewer (criteria from this doc, not the author's reasoning) → a fix
only for confirmed findings → the next item. Every agent gets the shared brief: this doc, the earlier
items' notes and `git diff --stat`, the mapped specs plus `npm run e2e:keystone` (not the full suite),
the hard rules (CLAUDE.md, fixtures only), a progress note per item, and its State line here. At the
end of each block: the full suite, a three-lens audit (correctness, docs against code, the standing
rules), fixes, stills of what changed, and a one-commit-per-block point for the user.
